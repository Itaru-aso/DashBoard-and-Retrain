# color 異常スコア算出方式への candidate1（z-score OR）導入パイロット v1.2

> 位置づけ: `retraining` spec の `design.md` を上書きせず、color の異常スコア算出方式に関する意思決定記録（ADR相当）として独立管理する。
> `.kiro/specs/retraining/dataset-export-root-migration.md`（学習データ参照方式の例外化）と同じ位置づけの、
> CLAUDE.md「やってはいけないこと」に対する追加の明示的例外。

## 目的 / 背景

現状、`training/` の異常スコア算出方式は monochro と color で異なる。

- **monochro**: `train/monochro.py` が検証用良品マップから画素位置ごとの `μ, σ` を較正し、
  `raw`（マップ最大値）と `z = max((map-μ)/σ)` をそれぞれ良品分布の分位点で `A, Z` に較正、
  推論時は統合スコア `max(raw/A, z/Z)`（OR判定）を `model.py` / `utils/scoring_transform.py` が出力する
  （`cand1` と呼称。`utils/candidate1_calib.py` が較正関数を提供）。
- **color**: `train/color.py` は `raw`（マップ最大値）のみ。z-score較正コード自体が存在しない。
  `model.py` の cand1 分岐は `if self.mode == "monochro" and cand1 is not None:` で monochro 専用にゲートされている。

ユーザーから、color で検出したい不良（小さい黒点異物・薄い汚れ）が低コントラストで raw 方式に構造的に弱いこと、
monochro 同様の z-score OR 方式を color に合わせるべきかの相談があった。オフライン検証（読み取り専用、
`training/` 配下のコードは変更せず、既存の学習済みモデル・検証データのみを使用）で以下を確認した。

### オフライン検証で確認した事実（color_no=001）

- **mu/sigma の再現性**: 較正用良品画像を2分割し独立集団間で比較。mu（背景平均パターン）は相関0.97で
  安定・再現（ヒートマップ上も縦方向の帯状構造が半々で一致）。sigma（背景ばらつき）は相関0.84で
  mu より不安定（n=200程度だと局所的なホットスポットが分割間で異なる位置に出る＝推定ノイズ）。
- **sigmaのレンジ**: min 0.012〜max 0.082（比6.85倍）。monochro実運用モデル（比5.4倍）と同程度の
  位置依存ノイズ不均一性が color にも存在する（z補正の理論的根拠が成立する）。
- **素朴な移植のFPR悪化**: 目標fpr=0.5%較正で、raw単独のホールドアウトFPRは分割条件により0.35〜2.60%、
  `max(raw/A,z/Z)` にすると分割条件により7.81〜8.16%まで悪化（raw単独の3〜16倍）。
  原因は88×116≒1万画素の map に対し max を取るため、位置ごとのσ推定ノイズが一部画素で極端に小さくなると
  そこがボトルネックになり誤検知に直結する（最大値統計の裾の重さ）。
- **欠陥43枚（実際の見逃し候補を含む）での検知率**: raw単独7〜19/43（分割条件次第）に対し、
  `max(raw/A,z/Z)` は11〜34/43（同条件比で概ね2倍前後）。z分岐がraw単独では埋もれる低コントラスト異常を
  実際に拾えていることを実データで確認。
- **FPR抑制に効くレバー**: σ空間平滑化（smooth窓3〜9）と較正枚数の増加（400→800）が明確に効く
  （FPRを1/3〜1/5に抑制）。σ floor（パーセンタイル下限）は効果が弱い。z側単独のfpr再較正
  （0.5%→0.02%まで100倍変えてもFPRがほぼ動かない）はほぼ無効。
  組み合わせ例 `smooth=7, sigma_floor_pct=50, fpr_z=0.05%` で、FPRをraw単独と同水準（0.35%）まで
  抑制しつつ欠陥検知15/43（raw単独7/43の2倍超）を達成する分割条件を確認。
- **限界**: 欠陥サンプルが43枚（color_no=001のみ）と少なく、較正/ホールドアウトの分割やシード次第で
  検知率・FPRの実測値にブレがある（同一条件でraw検知7〜13/43、unified検知11〜15/43の範囲でブレる）。

## 決定事項

1. **スコープ境界**: color_no='001' のみパイロット導入。他の color_no は現状の raw 方式を維持する。
   色によってテープ・チェーンの印字パターンや境界の位置が異なり、001で有効なパラメータが
   他色でも同様に効くかは未検証のため。
2. **実装方式**: `train/color.py` に config opt-in フラグ（例: `candidate1.enabled`、デフォルト `false`）を追加し、
   有効時のみ `train/monochro.py` の cand1 較正ブロック（L706-733相当）と同様の較正を行い、
   `para.json` に `cand1_enabled`/`cand1_mu`/`cand1_sigma`/`cand1_A`/`cand1_Z`/`cand1_T` を保存する。
   `cand1_enabled=false`（デフォルト）の他 color_no は既存の `para.json`（cand1キー無し）のまま、
   後方互換が保たれる（`model.py` の `load_para` は既に `para.get('cand1_enabled', False)` でゲート済み）。
3. **`model.py` のモードゲート緩和**: `if self.mode == "monochro" and cand1 is not None:` を
   `if cand1 is not None:` に変更する。有効/無効は既に `para.json` の `cand1_enabled` で制御されており、
   mode による二重ゲートは不要な制約であるため。
4. **`utils/candidate1_calib.py` の拡張**: `compute_mu_sigma` に `sigma_smooth`（空間平滑化窓、デフォルト無効）・
   `sigma_floor_pct`（パーセンタイルfloor、デフォルト無効）をオプション引数として追加する。
   デフォルト無効＝monochro の既存呼び出しへの影響なし（後方互換）。
5. **color_no='001' の初期デフォルト値**: `sigma_smooth=7, sigma_floor_pct=50, fpr_raw=0.5%, fpr_z=0.05%`
   （A・Zは独立したfprで較正する。理由は決定8参照）。
   上記オフライン検証で「FPRをraw単独と同水準に抑えつつ欠陥検知を概ね2倍にする」組み合わせとして
   確認した値だが、**固定値ではなく初期値**として扱う。実際の学習時には production の validation split
   （`train/good` の20%、color_no='001' は約455枚）で mu/sigma/A/Z を再較正する。
   オフライン検証で使用した `test/good`（976枚）とは異なる画像集合であるため、
   学習時に実測されるFPR/検知率はオフライン検証の数値と一致しない前提で運用する。
6. **本番投入前検証**: 学習後に生成される `para.json` のFPR/検知率を、既存欠陥テストセット（43枚）で
   再確認する。追加欠陥データの収集は当面行わない（ユーザー確認済み）。43枚が唯一の検証基盤であるという
   前提上のリスクを受容し、運用開始後に新たな欠陥事例が集まった場合を再較正のトリガーとする。
7. **ロールバック経路**: config opt-in フラグを `false` に戻して再学習するか、あるいは配信済み ONNX の
   `para.json` 相当メタデータの `cand1_enabled` を無視する（`model.py` のゲートで対応）ことで、
   即座に raw 方式へフォールバックできる。
8. **A/Zの独立fpr較正（2026-07-27追記）**: `_calibrate_cand1` は当初 raw(A)・z(Z) を単一の `fpr` で
   較正していたが、実際の `model.forward()` を通した検証で「FPRだけ大きく悪化し検知率の上乗せが無い」
   という結果になった（詳細は「実装後の追加知見」節）。原因は Z が緩すぎたことと判明したため、
   `fpr_raw`（A用、既定0.5%）・`fpr_z`（Z用、既定0.05%）を分離した。`utils/candidate1_calib.py` の
   既存関数は変更不要（`calib_AZ` を2回、異なる `fpr_pct` で呼ぶだけ）。

## 採用理由

- オフライン検証（実欠陥データ43枚、color_no=001）で、raw単独の検知率（7〜19/43、分割条件次第）に対し
  z分岐追加で2倍前後（11〜34/43）に改善することを確認済み。ユーザーが指定した検出対象
  （小さい黒点異物・薄い汚れ）は低コントラストで raw 方式に構造的に弱いタイプであり、
  この結果は理論的な予想と整合する。
- FPR悪化はσ平滑化+floor+較正枚数で raw単独と同水準まで抑制可能なことを確認済み
  （ユーザー許容度「raw同水準まで」と合致）。

## 検討した代替案と不採用理由

1. **現状維持（raw方式のまま）**: 検知率不足（見逃し）を許容することになり、ユーザーが明示した課題
   （小さい黒点異物・薄い汚れの検出強化）を解決しない。不採用。
2. **全 color_no へ無条件展開**: 色ごとの背景ムラ構造の違いが未検証であり、001で有効なパラメータが
   他色でFPRを悪化させるリスクを排除できない。ユーザーが「001でパイロット」を選択したため不採用。
3. **z側だけ独立にfpr再較正して抑制**: オフライン検証で fpr を0.5%→0.02%まで100倍変えても
   FPRがほぼ動かないことを確認済み（裾が重いため単独では無効）。不採用
   （ただし smooth/floor との併用パラメータの一構成要素としては残す）。
4. **欠陥データを拡充してから最終判断**: ユーザー確認により拡充不可のため不採用。
   43枚での判断リスクを本ドキュメントに明記し受容する。

## Consequence（残るリスク）

- 43枚という小さいサンプルに基づく較正のため、実運用開始後にFPRが想定を超える可能性がある。
  config opt-in フラグ off による raw 方式への即時フォールバック経路を用意する。
- 較正枚数は color_no ごとの validation split 枚数に依存する（001は2277枚と十分だが、
  将来パイロット拡大時は他色の枚数を要確認）。

## 実装計画（`.kiro/specs/retraining/tasks.md` タスク19〜23に対応）

TDD（RED→GREEN→REFACTOR）で4ステップに分解し、既存の学習ループ本体（`train/monochro.py`・
`train/color.py`の既存学習部分）には触れず、末尾の較正処理のみを追加する。

1. **`training/utils/candidate1_calib.py`（拡張・後方互換）**: `compute_mu_sigma(maps, sigma_smooth=1,
   sigma_floor_pct=None)` に平滑化（`scipy.ndimage.uniform_filter`）・floor（パーセンタイル下限）の
   オプション引数を追加。デフォルト値では既存の `monochro.py` 呼び出しと完全に同じ結果になること（後方互換）
   を回帯テストで確認する。新規 `training/tests/test_candidate1_calib.py`（純粋関数・モデル不要で高速）。
2. **`training/model.py`（1行変更）**: `if self.mode == "monochro" and cand1 is not None:` →
   `if cand1 is not None:`。有効/無効は `para.json` の `cand1_enabled` で既に制御されているため、mode条件は
   不要な制約（決定3）。`test_efficientad_full_model_regression.py` に `mode='color'` + cand1指定の新規ケースを
   追加（TDD RED→GREEN）。`compute_anomaly_score` 自体はmode非依存のため `test_scoring_transform.py` 等は
   変更不要（既存green維持を確認するのみ）。
3. **`training/train/color.py`（新規ブロック追加、既存学習ループは無改変）**: `train_color()` 末尾の
   閾値計算後、config opt-in（`cfg.candidate1.enabled`、デフォルト`false`）時のみ較正処理を実行。較正ロジックは
   `_calibrate_cand1(cand1_maps, sigma_smooth, sigma_floor_pct, fpr)` として関数化し、合成データ（小さいダミー
   map配列）で単体テストする（`train_color()` 全体を回す統合テストはしない）。`monochro.py` は一切変更しない。
4. **`training/conf/config.yaml`（設定追加）**: `candidate1: {enabled: false, fpr: 0.5, sigma_smooth: 7,
   sigma_floor_pct: 50}` をデフォルト追加（`enabled: false` のため他色は無変更のまま安全）。
   color_no=001 のパイロット学習時のみ CLI オーバーライド（`candidate1.enabled=true`）で有効化する。
5. **（手動検証）**: color_no=001 を `candidate1.enabled=true` で実学習し、生成された `para.json` の
   FPR/検知率を欠陥テストセット（43枚）で確認する。決定6の目標（FPRがraw単独と同水準）を満たすか確認し、
   満たさない場合は `sigma_smooth`/`sigma_floor_pct`/`fpr` を調整の上、本ドキュメントに実測値を追記する。

## 実装後の追加知見（2026-07-27）

実装（タスク19〜22）完了後、タスク23（手動検証）に着手する過程で advisor レビューと実データ検証により
以下が判明し、上記の決定事項・実装計画を更新した。

### edge_mask 規約の不整合（バグ、修正済み）

`train/color.py` の cand1_maps 収集が `slice_edge_excluded`（幅縮小）を使っていたが、
`utils/scoring_transform.py` の cand1 分岐は推論時に `apply_edge_mask_zero`（フル幅・両端0埋め）を
適用してから mu/sigma と減算するため、`edge_mask_w>0`（color本番=2）では mu/sigma と map_combined の
形状が不一致になり `model.forward()` が失敗する不整合があった。monochro は `edge_mask_w=0` のため
両者が no-op で一致し、これまで顕在化していなかった。`apply_edge_mask_zero` に統一する修正と、
edge_mask_w>0 での実forward回帯テストを追加した。

### 単一fprでのFPR悪化と原因診断

修正後、既存学習済みモデル＋新規較正（当時: 単一 `fpr=0.5%`, `sigma_smooth=7`, `sigma_floor_pct=50`）を
実際の `model.forward()` で検証したところ、FPR 2.95%（目標0.5%相当）・欠陥検知19/43（raw単独と同値、
上乗せ無し）という結果になった。オフライン切り分け実験（キャッシュ済みマップでの数値実験）により、
原因は2つと判明:
1. **A/Z単一fprの設計ミス**（実在・再現性あり）: Zをraw用と同じ緩いfprで較正すると発火しやすくなり
   FPRだけ悪化する。fpr_zを厳しく分離すると改善する（決定8で修正）。
2. **較正サンプル(400枚)自体の分散が大きい**（データ由来）: `test/good`(976枚)のraw_maxを全数確認した
   ところ、中央値0.25に対し上位5〜10枚が1.5〜2.9という明確な外れ値だった。目視確認した上位3枚には
   いずれも小さい黒点状の斑点が実際に写っており、**検出したい不良に近い境界的な良品画像**だった。
   A/Zはp99.5等の極端分位点を400枚程度の小標本から推定するため、この少数の外れ値画像が較正用/
   ホールドアウトのどちらに入るかで結果が大きく変動する。zero規約とslice規約の差自体は小さく
   （誤差レベル）、主因ではなかった。

### データセット側の対応（ユーザー実施）

上記の境界画像について `train/good`（2277枚）側も同様に確認したところ、同じパターン（上位7枚程度が
明確な外れ値、目視で黒点を確認）が見られた。ユーザーが目視確認の上、`export_root` 側の該当画像を
good カテゴリから defect(ng) カテゴリへ物理移動（正解ラベル修正）し、`3_pool`/`4_dataset` を
`process_annotated_images()` + `split_pool_to_dataset()` で再構築した（color: good 3253→3164枚
（-89枚）、defect 228枚に増加。13枚は目視確認済み、追加分はユーザーが提示リストから判断）。
これは学習アルゴリズム本体ではなくデータ（正解ラベル）の修正であり、CLAUDE.mdの学習ロジック不可侵
方針の対象外。

### 影響

- タスク23（手動検証）は、上記のコード修正（edge_mask統一・fpr分離）と更新後のデータセットの両方を
  反映した上で再実行する。
- 較正サンプルの分散問題は今回の枚数（400程度）では解消しきれない可能性があり、決定6の「43枚のみで
  判断」というリスク受容は維持しつつ、**A/Zの実測値は学習ごとにブレる前提**であることを明記する
  （固定値として期待しない）。

### 最終検証結果（2026-07-27、edge_mask修正 + fpr_raw/fpr_z分離 + ラベル修正後データセット）

タスク23の手動検証は、既存学習済みモデル（.pth重み）に後付けでcand1較正を行い、実際の
`EfficientADFullModel.forward()` を通して測定する方式で実施した（advisorの助言: cand1較正はpara.json
側の後付けであり .pth重みは較正結果に依存しないため、再学習なしで検証可能）。

```
color_no=001, edge_mask_w=2, good=949枚, defect=71枚（ラベル修正後）
較正: sigma_smooth=7, sigma_floor_pct=50, fpr_raw=0.5%, fpr_z=0.05%（決定8のデフォルト値）
A=0.6477, Z=30.006

FPR（ホールドアウト良品549枚）: raw単独 0.91% → unified 1.09%（+0.18pt）
欠陥検知（71枚）: raw単独 45/71 → unified 45/71（変化なし）
```

**判定**: 決定6の目標「FPRがraw単独と同水準」は達成（+0.18ptの微増のみ）。検知率の上乗せは
今回の実測ではゼロだったが、悪化もしていない。

**検知率が今回上乗せ無しだった点の解釈**: データセット修正で「小さい黒点はあるがラベルはOK」だった
境界画像の多くがdefect側に移動した。これらの画像はraw異常スコアが元々高かった（median比6〜11倍）ため、
71枚の欠陥セットの中で**raw単独でも既に検知できる「簡単な」defectとして寄与している**可能性が高い。
すなわちデータラベル修正とz分岐は同じ問題（低コントラストな小さい黒点の見逃し）に対して部分的に
重複する対策であり、データを修正した後に残る「rawでは拾えない」欠陥がこの71枚の中には今回多く
残っていなかった、と考えられる。較正サンプルの分散が大きいこと（本節前半参照）も踏まえ、これは
1回の実測値であり確定的な結論ではない。

**結論**: FPR目標を達成しているため、タスク23は完了とする。z分岐による追加の検知率向上効果は
今回の実測では確認できなかったが、悪化もしていないため、パイロット（color_no=001、config opt-in）
としての導入自体は妥当と判断する。運用開始後、新たな欠陥事例が集まった際に効果を再評価する
（決定6のトリガーと同じ）。

## color_no=316 での再現性確認（2026-07-28）

001以外の色でも同じ傾向が再現するかを確認するため、color_no=316（export_root同一データセット内、
good 4094件・ng 393件）でも同様の検証を実施した。

### 既存モデルでの検証（ラベル修正前、5シード）

001と同じ手順（既存学習済みモデル＋オフライン後付け較正、`smooth=7, floor=50, fpr_raw=0.5%, fpr_z=0.05%`）
で5シード検証した結果、**5シードすべてでunified＝raw単独と完全に一致**（FPR・検知率ともに差ゼロ）。
mu相関0.99・sigma相関0.91（001より高く較正はむしろ安定）。001の最終結果（上乗せほぼ無し）と整合する、
再現性のある結果だった。

### ラベル修正後の実学習での検証

train/good・test/good内の外れ値的な良品画像（001と同様、目視で黒点等を確認できるもの）をユーザーが
export_root側でng（defect）カテゴリへ再ラベル。3_pool/4_dataset再構築後、color_no=316を
`candidate1.enabled=true`で実際に学習（40 epoch, 25000 step上限, GPU実行）。

生成された`para.json`: `cand1_A=6.5424, cand1_Z=97.624, threshold(raw方式)=7.3557`。
実forward検証（test/good 1221枚, test/defect 123枚）:

```
FPR: raw単独 0.00% → unified 0.00%（変化なし）
欠陥検知: raw単独 1/123（0.8%） → unified 35/123（28.5%）
```

一見、z分岐が34件も追加検知した大きな改善に見えたが、raw_max分布を確認したところ**別の原因**と判明した。

```
test/good  raw_max: min=0.08 p50=0.16 p99.5=1.00 max=1.55
test/defect raw_max: min=0.11 p50=1.97 p90=5.25 max=7.54
```

良品と欠陥の分離は非常に明確（良品最大値1.55 vs 欠陥中央値1.97）で、閾値を2.0前後に設定するだけで
FPR0%を維持しつつ欠陥の大半を検知できるはずのデータだった。しかし実際の`threshold`（7.3557）は
**欠陥の最大値(7.54)に迫るほど過大に較正**されていた。これは較正用validation分割（train/goodの20%側、
学習ごとにランダムに変わる）に外れ値的な良品画像が1枚でも混入すると、99.5パーセンタイルという
極端分位点の推定が大きく崩れるという、本ADRで既に指摘していた問題（決定8前半の原因診断②）が
実際に発生したものと考えられる。z側の較正（A/Zの計算式は異なる）がたまたま同じ外れ値の影響を
受けなかったため、rawの較正失敗をunifiedが結果的に救った、という構図であり、**z分岐の機構自体が
検出力を持つことを示す証拠にはならない**。

### 結論（001・316を踏まえた最終判断）

1. **candidate1（z-score OR）の効果は、正しく較正された条件下では確認できなかった**（001: 実測で
   検知率上乗せゼロ。316: ラベル修正前5シードで一致ゼロ。316のラベル修正後の「改善」はraw較正失敗の
   artifact）。2色・複数シードでの再現性のある結果であり、`candidate1.enabled`は**false推奨**とする。
2. **別の、より重要な発見**: 既存のraw閾値較正方式（`np.quantile(scores_np, 0.995)`。candidate1とは
   無関係に全color共通で使われている既存ロジック、本ADRの変更対象外）が、較正用validation分割に
   混入する少数の外れ値的な良品画像1枚だけで閾値を大きく踏み外す脆弱性を持つことが、316の実学習で
   実際に確認された。この問題はcolor_no=316に限らず、candidate1を使わない他のcolor番号・monochroの
   既存運用にも当てはまり得る、本パイロットのスコープを超えた既存コードの課題である。CLAUDE.mdの
   例外範囲外（学習ループ・color学習ロジック本体）のため本パイロットでは修正しないが、別途の
   検討課題として記録する。

## 本番採用スコアの決定（2026-07-29）

ユーザーから「raw/Aで出しているという認識だが、Aを算出しない単純なrawはどうなっているか」との確認があり、
5種のスコア（raw_score正規化前・raw_over_A・z_score・z_over_Z・unified_score）を比較検証した。

### 決定9: 本番は `raw_score`（正規化前・人間が閾値を手動設定）を採用する

- **採用**: `raw_score`（異常マップのmax、A/Zによる正規化なし）。人間が良品/欠陥のスコア分布を見て
  閾値を手動設定する運用とする（ユーザー提案）。
- **不採用**: `raw_over_A`（Aが外れ値混入で暴走する既存の脆弱性を継承）、`z_score`/`z_over_Z`/
  `unified_score`（z分岐は001・316・複数シードで検知への寄与ほぼゼロと確認済み、決定1と同じ理由）。

### 316での検証（実際にONNXがcandidate1無効時に出力する pad+interpolate max を使用）

```
閾値   FPR(good 1221枚)   検知率(defect 123枚)
0.9    0.57%              65.0%
1.0    0.33%（4枚）        65.0%（80枚）
1.1    0.25%（3枚）        65.0%
1.2    0.08%（1枚）        61.8%
```

ユーザー提案の1.0〜1.2帯の中では**1.0〜1.1が最適点**（検知率65%を維持しつつFPRが最小）。

### 決定10: raw_scoreの限界（recallの上限）を明記する

閾値0.8〜1.1で検知率は約65%が頭打りになる。欠陥123枚中の残り約35%はraw_scoreが良品分布と重なって
おり（一部は良品の中央値未満）、**このモデル・このスコアではどの閾値でも検出不可能**。手動閾値調整は
決定8で発覚した較正の「暴走」（A=6.54という異常値）を直すものであり、検出できる上限（recallの
天井）そのものを上げる効果はない。この2つを混同しないこと。

### 発見（決定11）: native-grid maxとpad+interpolate maxの尺度不整合（candidate1と無関係の既存課題）

`train_color()`が計算する`para.json['threshold']`は較正時の**native grid（88×120）でのmax**を
p99.5等で分位点較正するが、candidate1無効時にONNX/`model.forward()`が実際に出力するのは
`pad(4,4,4,4)→bilinear interpolate(384×512)→max`という**別の計算**の結果である。較正用600枚で
比較すると、native側で計算したp99.5閾値(0.9148)は、pad+interpolate分布上ではp99.67%点に相当し、
**意図した目標FPR(0.5%)よりも実効的にやや厳しめ(保守的)にずれる**（両側で6%程度の値のずれ、
n=316サンプルでの実測）。危険な方向（FPRが甘くなる）のズレではないが、意図した較正基準からの
系統的なズレであり、**candidate1の有無に関わらず全color・monochroの既存ロジックに恒常的に
存在する**設計不整合である。CLAUDE.mdの例外範囲外（学習ループ本体）のため本パイロットでは
修正しないが、決定9のスコア採用時にはこの尺度（pad+interpolate側）で閾値スイープを行う必要がある
ことを明記する（上記表は既にpad+interpolate側で実施済み）。

### recall天井（65%）に対する提案（モデル側の課題、advisor所見）

閾値調整では解決しない残り35%の欠陥について、モデル側の改善案を以下に列挙する（いずれも
**提案のみ・未実装**。実装する場合は方針提示→承認のプロセスが必要）。

1. **見逃し画像の目視確認**: raw_scoreが良品分布と重なる欠陥画像を実際に開いて確認する。
   本当に視覚的に微弱な欠陥か、ラベル自体の誤りか、あるいは「小さい黒点」とは異なる欠陥タイプ
   （ST差分ベースの手法が原理的に苦手な種類）かを見分ける。原因により対策が変わるため、
   これが最初にやるべき診断。
2. **学習データの拡充**: 見逃し欠陥タイプの学習画像が不足している場合、そのタイプを追加収集する
   （データ追加は学習ロジック本体の変更に該当しない）。
3. **channel_weights設定の再チューニング**: 既存の`channel_weights.supervised_power`/
   `unsupervised_power`等は既に公開されている設定値であり、学習ループ・モデル構造は変更せず
   値の見直しのみで済む可能性がある。
4. **学習の収束確認**: 今回の316実学習はearly_stop_patience=4で停止した。学習ステップ数や
   patience等の既存ハイパーパラメータ（config値）を変えて再学習し、収束状況を比較する余地がある。
5. **モデル構造・スコア集約方式の変更**（max以外の集約、アーキテクチャ変更等）: 学習ループ・
   モデル構造の変更に該当するため、CLAUDE.mdの例外範囲外。検討する場合は別途承認が必要。

color_no=316の`para.json`の`cand1_enabled`を`false`に変更し（`cand1_*`の他の値は参考のため保持、
元ファイルは`para.json.cand1enabled.bak`に退避）、`deploy.export_model()`でraw方式のONNXを再エクスポート

0.9  | 0.57%             | 65.0%
1.0  | 0.33%（4枚）       | 65.0%（80枚）

### 決定12: 最終結論

- **本番採用スコア**: `raw_score`（正規化前、決定9）
- **推奨閾値（316・このモデル限定）**: 1.0〜1.1（人間が良品/欠陥分布を確認して設定。決定9の運用方針）
- **candidate1**: `enabled=false`をデフォルトのまま維持（決定1・8のとおり、効果未確認）

  別途検討する。

### 発見（決定13）: export_root側のgood/defectラベル矛盾（重複データ、candidate1と無関係）

決定10の提案1（見逃し画像の目視確認）を実施した過程で発覚した。color_no=316の見逃し欠陥画像
（raw_score<1.0の43枚）を実際に開いて確認したところ、一部（score 0.16, 0.30等）には視覚的に
微弱な黒点が確認できたが、一部（score 0.0962の`NG_image_103244_303_1.bmp`等）は4分割2倍拡大
しても**視覚的な異常が全く見当たらなかった**。原因を調査した結果、**同一内容（MD5完全一致）の
画像ファイルが、export_root側でgood/defect両方のカテゴリに矛盾して重複配置されている**ことが
判明した。

```
test/good ⇔ test/defect（同一データセット内）  : 3件
train/good ⇔ train/defect（同一データセット内）: 6件
test/good ⇔ train/defect（split跨ぎ）          : 6件
test/defect ⇔ train/good（split跨ぎ）          : 5件
合計20件（color_no=316のみで確認。他colorは未確認）
```

例: `NG_image_102920_134_bottom.bmp`が、export_root上で good カテゴリ
（`019ef71f-b445-...`）に`_top`/`_bottom`両方、ng カテゴリ（`019ef75b-6eab-...`）に`_bottom`のみ、
という形で重複配置されていた（同一timestamp・同一カメラ面のファイルが2カテゴリに存在）。

**影響**:
- test評価上は、見逃し43枚中2件がこの矛盾に直接起因（同名ファイルがgood側にも存在＝ラベル自体が
  自己矛盾）。
- より重要なのは、**train側にも同じ矛盾が存在する**ため（train内6件・split跨ぎ11件）、学習時に
  同一の見た目の画像に対してgood/defect両方の教師信号を与えている可能性がある。recall天井65%
  （決定10）の一因が、モデルの学習不足ではなく**学習データ自体の矛盾**にある可能性を示唆する。

**スコープ**: これは`export_root`を生成する別機能（CLAUDE.md記載の「本タスクのスコープ外」）の
データ品質課題であり、training/側では修正できない。アノテーションシステム側の担当箇所への
報告・確認が必要な事項として記録する。他のcolor番号（001等）・monochroでも同様の重複が
存在するかは未確認。

### 決定14: 重複ラベル解消（ユーザー実施）と再学習による効果検証（2026-07-29）

ユーザーが決定13で発見した20件の重複について、`export_root`のgood側カテゴリから該当ファイルを
削除（ng側は保持。バックアップは`backup/export_root_316_good_dup_backup_*/`）。3_pool・4_datasetを

を検証した結果:

```

0.8  | 1.06%(13枚) / 65.0%(80枚) | 0.82%(10枚) / 68.3%(84枚)

### 決定15: 2回目のラベル見直し + 学習収束確認 + channel_weights再チューニング（2026-07-29）

ユーザーが`export_root`のラベルを再度見直した（good: 4050→4031→4031枚台、defect: 411→379枚、
2回目の見直しでは一部defect→goodの戻しも含む）。3_pool・4_datasetを再構築後
（good: train 2822/test 1209、defect: train 264/test 115）、決定10の提案4（学習収束確認）・
提案3（channel_weights再チューニング）を**1回の学習に統合**して実施した:

1. **学習収束確認**: `max_train_step`を25000→35000に増やし、target_step(30840、データ件数変化で
   再計算)を下回らないようにキャップを外した（前回は25000でキャップされ、target_step=31360に
   到達していなかった）。
2. **channel_weights再チューニング**: `supervised_power`を10→15に変更（1デルタのみ、ユーザー
   選択）。

2つの変更を分離せず統合して検証したため、どちらの効果か個別には特定できないが、組み合わせの
効果として実測した。実際に再エクスポートしたONNX(raw方式)で1324枚（test/good 1209枚・
test/defect 115枚）を検証した結果:

```
閾値  | 決定14時点(旧モデル) FPR/検知率 | 決定15(新モデル) FPR/検知率
0.55  | (未計測)                        | 0.66%(8枚)  / 80.9%(93/115)
0.60  | (未計測)                        | 0.50%(6枚)  / 77.4%(89/115)
0.65  | (未計測)                        | 0.33%(4枚)  / 73.9%(85/115)
0.80  | 0.82%(10枚) / 68.3%(84/123)      | 0.17%(2枚)  / 64.3%(74/115)
0.90  | 0.58%(7枚)  / 67.5%(83/123)      | 0.08%(1枚)  / 60.0%(69/115)
```

`para.json['threshold']`（native較正値）も 7.36→6.96→**4.30** と、外れ値混入の影響が薄れる方向に
改善している（決定8・13で指摘した較正脆弱性の根本解決ではないが、データ品質改善に伴い間接的に
安定化している）。

**結果**: 良品側のスコア分布が大幅に締まった（good最大値 1.67→**0.97**）。同程度のFPRで比較すると
（例: 閾値0.65のFPR0.33% ≒ 決定14時点の閾値1.0のFPR0.33〜0.41%）、検知率は65.0%→**73.9%**
（+8.9pt）。より緩いFPR（0.5〜0.66%）まで許容すれば77.4〜80.9%まで改善する。決定14単体
（データ修正のみ、+3〜4pt）よりも大幅に効果が大きく、**学習収束確認・channel_weights再チューニング・
2回目のデータ品質改善のいずれか（または組み合わせ）が有効に働いた**と判断できる。

**新モデルでの推奨閾値**: **0.6〜0.65**（FPR 0.33〜0.50%、検知率73.9〜77.4%）に更新する
（決定14の0.8〜0.9から変更。決定10の運用方針どおり、モデルが変わるたびに人間が分布を
再確認する）。

**限界**: 2つの変更（学習収束・channel_weights）を同時に投入したため個別の寄与度は不明。
今後さらに追い込む場合は、変更を1つずつ切り分けて再学習・比較することが望ましい。また
FPR0%に近い閾値（0.8〜0.9）まで上げると検知率は旧モデルより低下する（64.3%/60.0%）ため、
「運用で許容できるFPRの水準」によって新旧どちらのモデル・閾値が有利かが変わる点に注意
（新モデルは低FPR領域では旧モデルに劣るが、中間FPR領域では明確に優れる）。

### 決定16: 学習収束確認・channel_weights再チューニングの切り分け検証（2026-07-30）

決定15の限界（2変更を同時投入したため個別寄与度が不明）を解消するため、決定15と同じ
再構築済みデータセット（good: train 2822/test 1209、defect: train 264/test 115）に対して、
2つの変更を1つずつ単独で適用した再学習を実施した。

- **実験A（学習収束確認のみ）**: `max_train_step`のみ25000→35000（`channel_weights.supervised_power`
  はデフォルト10のまま）
- **実験B（channel_weights再チューニングのみ）**: `channel_weights.supervised_power`のみ10→15
  （`max_train_step`はデフォルト25000のまま）

実際に再エクスポートしたONNX（raw方式）で同一の1324枚（test/good 1209枚・test/defect 115枚）を
検証した結果:

```

0.60  | 0.58%(7枚)  / 80.9%(93/115)       | 0.41%(5枚)  / 75.7%(87/115)            | 0.50%(6枚)  / 77.4%(89/115)
0.65  | 0.41%(5枚)  / 80.0%(92/115)       | 0.41%(5枚)  / 72.2%(83/115)            | 0.33%(4枚)  / 73.9%(85/115)
0.70  | 0.25%(3枚)  / 77.4%(89/115)       | 0.41%(5枚)  / 71.3%(82/115)            | 0.33%(4枚)  / 67.8%(78/115)

0.80  | 0.25%(3枚)  / 73.0%(84/115)       | 0.25%(3枚)  / 67.8%(78/115)            | 0.17%(2枚)  / 64.3%(74/115)
```

**結果**: 同程度のFPR水準（0.25〜0.5%帯）で比較すると、**実験A（学習収束確認のみ）が3条件中最も
検知率が高い**（例: FPR0.41%で検知率80.0%）。実験B（channel_weightsのみ）は単独でもベースライン
（65.0%、決定14参照）より改善するが、実験Aより効果が小さい（同FPR帯で71〜76%程度）。

意外な点として、**決定15の「両方統合」モデルは、実験A単独よりも同FPR帯で検知率が低い**
（例: FPR0.33〜0.41%帯で実験A 80.0% vs 統合73.9%、FPR0.25%帯で実験A 77.4% vs 統合67.8%）。
すなわち学習収束確認とchannel_weights再チューニングを同時投入すると、**負の相互作用**が生じている
可能性が高い。両者を独立に効かせるより、`max_train_step`の増加（学習収束）だけで十分な効果が
得られ、`channel_weights.supervised_power`の追加変更はむしろ足を引く方向に働いたと判断できる。

**結論・推奨**: 316の本番候補モデルは、**実験A（`max_train_step=35000`のみ、`channel_weights`は
デフォルト10のまま）を採用**する。推奨閾値は**0.65〜0.70**（FPR 0.25〜0.41%、検知率77.4〜80.0%）。
決定15の統合モデル・`channel_weights.supervised_power=15`への変更は不採用とする。

**限界**: この切り分けはmax_train_step・supervised_powerの各1点のみの比較であり、両者の交互作用が
なぜ負に働くかの機序（例: 学習が長く回ることでsupervised_powerの重み付けが過学習方向に振れる等）は
未解明。今後さらに追い込む場合は、supervised_powerを10のまま固定し、max_train_stepをさらに
伸ばした場合の効果（収益減衰点の確認）や、001など他色番号での再現性確認が次の検証候補となる。

### 決定17: epochs延長による収益減衰点の確認（2026-07-30）

決定16の限界で挙げた「学習をさらに伸ばした場合の効果」を検証するため、`max_train_step`の
仕組みを再確認した。`train/color.py:286-294`の実装は
`cfg.train_step = min(target_step, max_train_step)`（`target_step = iterations_per_epoch * epochs`、
`epochs`は既定40で固定）であり、**`max_train_step`は上限（キャップ）にすぎず、`target_step`を
超える値を指定しても学習量は変わらない**ことが判明した。実際、実験A（`max_train_step=35000`）の
学習ログでも`train_step: 30840 (target=30840, cap=35000)`となっており、実質的な学習量は
target_step=30840のままだった。したがって「学習をさらに伸ばす」ための正しいレバーは
`max_train_step`ではなく`epochs`である。

この事実を踏まえ、`epochs`のみ40→50に変更（`max_train_step`は45000に上げてキャップが効かないように
調整、他は実験Aと同一: `channel_weights`デフォルト・`candidate1.enabled=false`）して再学習した。
実際にtrain_step=38550（target=38550、キャップなし、early stopping未発動）で学習が完了し、
同一テストセット（test/good 1209枚・test/defect 115枚）で検証した結果:

```
閾値  | 実験A(epochs=40, train_step=30840) FPR/検知率 | epochs=50(train_step=38550) FPR/検知率
0.60  | 0.58%(7枚)  / 80.9%(93/115)                    | 0.74%(9枚)  / 83.5%(96/115)
0.65  | 0.41%(5枚)  / 80.0%(92/115)                    | 0.41%(5枚)  / 83.5%(96/115)
0.70  | 0.25%(3枚)  / 77.4%(89/115)                    | 0.33%(4枚)  / 81.7%(94/115)
0.75  | 0.25%(3枚)  / 73.0%(84/115)                    | 0.25%(3枚)  / 78.3%(90/115)
0.80  | 0.25%(3枚)  / 73.0%(84/115)                    | 0.25%(3枚)  / 77.4%(89/115)
```

**結果**: 同一FPR水準で比較すると、epochs=50はepochs=40（実験A）を一貫して上回る
（例: FPR0.41%で検知率80.0%→**83.5%**、FPR0.25〜0.33%帯で73.0〜77.4%→77.4〜81.7%）。
**収益減衰点にはまだ達していない**（学習を伸ばすほど改善が続いている）。

**結論・推奨**: 316の本番候補モデルを実験Aからepochs=50モデルに更新する。推奨閾値は
**0.65〜0.70**（FPR 0.33〜0.41%、検知率81.7〜83.5%）。決定16の推奨（実験A、epochs=40）は
このモデルに置き換える。

**限界**: 収益減衰点（epochsを伸ばすほど改善が止まる点）はまだ観測できていない。さらに
epochs=60等で追い込む余地があるが、学習時間は線形に増加する（epochs=50で約100分、
epochs=40の約1.25倍）。過学習のリスク（early stopping未発動が続く場合、val_loss監視の
妥当性を別途確認する必要がある）にも留意する。ユーザー判断により、epochs=50を現時点の
最良として確定し、収益減衰点の追い込み（epochs=60）は行わない。

### 決定18: augmentation強度の切り分け検証（進行中、2026-07-30）

検出対象「小さい黒い点のような異物や薄い汚れ」に対し、augmentationが信号を消している
可能性を検証する。決定17のepochs=50モデル（epochs=50, max_train_step=45000,
channel_weightsデフォルト）をベースラインとし、以下を1つずつ切り分けて再学習する。

#### 実験1: penalty_augmentation.random_erasing_p 0.1→0

学習は`train_step=38000/38550`でEarly stopping発動（目標の98.6%、ほぼ全量学習済みで
学習量の差は無視できる水準）。同一テストセット（test/good 1209枚・test/defect 115枚）で検証:

```
