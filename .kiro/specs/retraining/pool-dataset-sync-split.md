# pool / dataset の同期化と撮像単位の安定分割（train/test 重複・付け替え未反映の解消・ADR）

- 日付: 2026-10-23
- 状態: 採用（ユーザー承認済み 2026-10-23。「1.改修してよい。2.プールから消す。3.そろえる。4.全色番」）
- 対象: `training/utils/split_manager.py`（`split_pool_to_train_test` のみ）、`training/dataset/manager.py`
  （`process_annotated_images` のみ）
- 関連: `calibration-selection-teacher-stats-validation-plan.md`（5-8 で付け替え未反映を特定）、
  `eval-calibration-leak-fixes.md` 決定3（撮像単位分割）

## 背景

全28色番の 3_pool / 4_dataset を調べた（2026-10-22、読み取りのみ）。中身が同一で別名の画像は 0 件。
重複はすべて同名または同一撮像（`_0`/`_1`）によるもので、原因は2つ。

1. **分割が実行毎に変わり、差分追加で両側に残る**（001・053・076・181・566・567）。
   `split_pool_to_train_test` は毎回 pool 全体を seed 固定でシャッフルして振り分けるため、pool が増える
   （または分割方式が変わる）と既存画像の行き先が変わる。コピーは「行き先に同名があるか」しか見ず、
   反対側の旧コピーも消さない。実測: 181 の重複 1330 枚は現行分割で train 665 / test 665 に分かれ、
   非重複の画像は全て現行分割と一致（053・001・566 も同様）。test/good の 62〜84% が train/good と同名。
2. **撮像単位化（2026-08-18, 4996afe）前の1枚単位分割が残っている**（075・316）。同名重複は 0 だが
   train/good と test/good で同一撮像が 778 / 808 件。現行分割と約3割が不一致。コード修正だけでは直らない。

加えて、`process_annotated_images` は pool へ差分追加するのみで、export_root 側で good→ng に付け替えられた
画像や export_root から消えた画像が pool に残る（001 color で 1099 枚が good_pool と defect_pool の両方、
495 枚が export から消えたまま good_pool に残存）。

## 決定

1. **分割を撮像ごとのハッシュで決める**（`split_pool_to_train_test`）。
   - 撮像キー＝ファイル名から `OK_`/`NG_` 接頭辞（検査時の AI 判定であり良否クラスではない）を外し、
     末尾の `_数字`（面）を除いたもの。
   - `md5(f"{seed}:{撮像キー}")` を [0,1) に写し、`train_ratio` 未満なら train。ほかの画像の有無に依存しない
     ため、pool が増えても既存撮像の行き先は変わらない。
   - **良品・不良で同じキー・同じ規則を使う**（ユーザー決定3）。片面だけ不良の撮像でも良品面と不良面が同じ側に入る。
   - 比率は撮像数の期待値として 0.7（厳密な `round(n*0.7)` ではない）。小 pool で片側が 0 になり得る。
2. **dataset を pool に同期する**。各クラスの train/test の画像のうち、行き先と違う側にあるもの・pool に無いものを削除する。
   戻り値に `removed`（削除枚数）を追加する。**pool のそのクラスが無い・空のときは dataset のそのクラスを消さない**
   （パス誤りの保護。567 monochro は good_pool が空で dataset にだけ良品 1520 枚があり、無条件同期だと失われるため）。
3. **pool を export_root に同期する**（`process_annotated_images`、ユーザー決定2）。各 pool から、export_root の
   対応クラス（invalid_flg=1 を除く）に存在しない画像を削除する。判定は export_root のファイル一覧（正規化後の名前）で
   行い、デコード失敗でスキップした画像は削除しない（一時的な読み取り失敗で既存コピーを失わないため）。
   **export_root のそのクラスに画像が1枚も無いときは pool のそのクラスを消さない**（共有の同期途中・フォルダ移動の保護。
   001 monochro は良品 121 枚が export_root の `001_temp` に移されており、無条件同期だと良品が0枚になるため）。
   このため、クラスの最後の1枚は自動では削除されない。
   さらに、**metadata に無いカテゴリのフォルダが binary 配下にあるときはその mode の削除をしない**（metadata が古い・
   書き込み途中だと付け替え先を判定できないため。2026-10-23 時点の実 export_root には該当フォルダ無し）。
   pool との比較は**ファイル名の大文字小文字を区別しない**（Windows では `_copy_if_new` が区別せず存在判定するため、
   区別すると拡張子の大小が変わった画像を消して再コピーしない）。
   **1クラスの削除予定が 20% を超え、かつ 10 枚を超えるときはそのクラスの削除をしない**（ユーザー決定 2026-10-23「1.a」。
   一覧の部分取得・export 生成途中での大量削除対策。比率は `common.pool_sync_max_delete_ratio` で変更でき、正当な大量付け替えは
   値を上げて再実行する。10 枚以下は小さいクラスが毎回止まらないよう対象外）。dataset 側（pool→dataset）は pool が正であり、
   移行時は撮像の約4割が必ず入れ替わるため対象外。
4. **全色番を作り直す**（ユーザー決定4）。当初は `training/_experiments/` に作ってから置き換える案だったが、
   ユーザー決定（2026-10-23「3_pool と 4_dataset を更新する形で作り直して」）により、実 3_pool / 4_dataset をその場で
   同期した（4_dataset は空き容量確保のためユーザーが事前に空にした。バックアップなし）。対象は 3_pool の29色番と
   3_pool_03czt8 の15色番。001 monochro の良品 121 枚は残す（決定 2026-10-23「2.a」。export の `001_temp` にあるため、
   空クラスのガードで残る）。

## 不採用の代替案

- **既存配置を尊重し新規分だけ分割する（stateful）**: dataset フォルダの状態に依存し、075・316 の旧分割を固定化する。
  新規が少数だと `max(1, round(n*0.7))` で常に train に寄るため不採用。
- **毎回 pool 全体から作り直す（現行方式＋全削除）**: pool が増える度に既存画像の側が入れ替わり、過去モデルの学習画像が
  test に入って評価が甘くなるため不採用。
- **`split_files_by_product` 自体をハッシュ方式に変える**: monochro・color・03CZT8 の train/val 分割（比率・較正入力は
  `color-train-good-only.md` でスコープ外）に波及するため不採用。同関数は無変更。

## スコープ外（指摘のみ）

- `create_split`（評価用 val/test 分割）も全体シャッフル・良品1枚単位の同じ弱点を持つ。現在どこからも呼ばれていない。
- export_root の同一画像が good と ng の両カテゴリにある場合は両 pool に入る（現行どおり）。決定1により少なくとも同じ側に入る。

## 影響

- **03CZT8 にも及ぶ。** `train/item_03czt8/pipline.py` も同じ `DatasetManager` を使うため、次回実行時に
  `3_pool_03czt8` / `4_dataset_03czt8` も同期（削除・振り分けの入れ替え）される。
- **残る危険**: 一覧が部分的に見えても、削除が上限以内（20% 以下または 10 枚以下）なら削除される。export_root に残って
  いれば次回の実行で戻る。分割側の削除はファイル名をログに出さない（件数 `removed` のみ）。
- 03CZT8 は同期後の計算で pool の削除・追加とも 0、train/test 跨り 0（`4_dataset_03czt8` は空から作成）。

- **全色番で比較の基準がリセットされる。** ハッシュ方式の行き先は旧分割と独立なため、どの色番も撮像の約4割が反対側へ移る
  （同期後の計算で 849 color でも良品 1280 枚が移動）。新しい test/good の約7割（0.7×0.3/0.3）は旧 train にあった画像になる。
  したがって移行前に学習したモデル（配信中モデル・0-4・5-7 の基準を含む）は新しい test では評価できず、再学習が必要。
- 本変更の後に `pipline.py` を通常実行すると、実 3_pool / 4_dataset が同期（削除を含む）される。決定4の作り直しで
  同期済みのため、以降の実行では export_root 側の変更分だけが反映される。

## 調査結果（2026-10-22〜23、読み取りのみ）

- 重複チェック（全28色番・両 mode）: 中身同一・別名は 0 件。train/good と test/good の同名重複は 001・053・076・181・566・567
  （test/good の 62〜84%）、同一撮像の跨りのみは 075・316。良品と不良の両方にある画像は 001（pool 1099 枚）・030（4 枚）のみ。
  集計: scratchpad `dup_all.csv`（セッション 67dbed10）。
- 現行分割との照合: 181・053・001・566 の同名重複は現行分割で train/test にほぼ半々（例 181: 665/665）、非重複は全て一致。
  075・316 は約3割が現行分割と不一致（撮像単位化前の分割が残存）。`OK_`/`NG_` 接頭辞違いで分かれる撮像は 0 件。
- 同期後の計算（書き込みなし・全色番）: 同名・同一撮像（良否問わず）の train/test 跨りとも 0 件。pool からの削除は
  良品 1829 枚・不良 306 枚（001 color 1594 枚〔export から消えた 495 枚はどのフォルダにも無い〕、001 monochro 121 枚、
  316・911・030・566・567・579 等）。
- 567 monochro の dataset 専用良品 1520 枚（`train/good`、2026-09-17 作成）は export_root・export_root_margin・全 pool の

## 検証基準

- `tests/utils/test_split_manager.py`: pool に撮像を追加して再実行しても既存撮像の側が変わらない／何度実行しても
  train と test の両方に入る画像が無い／旧方式で両側に置かれた画像が片側に整理される／良品面と不良面が同じ側に入る／
  pool から消えた画像は dataset からも消える／小 pool でも全画像がちょうど1回置かれる／pool が無い・空のクラスは
  dataset を消さない。
- `tests/dataset/test_manager_export_root.py`: export_root で付け替え・削除・invalid 化された画像が pool から消える／
  デコード失敗の画像は既存コピーを残す／export_root のクラスが空なら pool のそのクラスを残す。
- 作り直した全色番で重複チェック（同名・同一撮像の train/test 跨り）が 0 件。
