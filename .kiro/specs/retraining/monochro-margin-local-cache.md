# monochro margin画像のローカル一時キャッシュ化 v1.0

> 位置づけ: `retraining` spec の `design.md` を上書きせず、`RawShiftImageFolder` の
> 読み込み元をネットワーク共有からローカル一時キャッシュへ切り替える意思決定記録（ADR）として
> 独立管理する。CLAUDE.md「学習ロジック変更不可」の**既存承認済み例外**
> （`training/train/monochro.py` の DataLoader 構築部分・`RawShiftImageFolder` 呼び出し方式）の
> 範囲内の変更であり、新規のCLAUDE.md例外は不要。

## 背景 / 問題

2026-08-19〜20、色番030・579の学習パイプライン（`pipline.py`）実行を実測した結果、
monochro学習ループ（30000 step、batch_size=4）が **5時間5分**（030）かかり、
並行実行されるcolor学習ループ（同31200 step、1時間25分）の約3.6倍の時間を要した。

実測ベンチマーク（`\\digi2\止水F色物画像検査\画像データ\export_root_margin\...`から60枚読込）:

| 処理 | 1枚あたり |
|---|---|
| ネットワーク読み込みのみ | 145.7ms |
| デコード＋クロップ＋リサイズ（CPU処理） | 38.8ms |

実効転送速度 16.4MB/s から逆算した理論スループット（6.7枚/秒）は、実測の学習速度
（1.64 it/s × batch4 = 6.56枚/秒）とほぼ一致した（誤差2%）。**ネットワーク帯域がmonochro
学習速度の支配的なボトルネックである**ことが定量的に確認された。

原因: `training/utils/raw_shift_dataset.py` の `RawShiftImageFolder.__getitem__` が、
撮像シフト不変性学習（`crop_offset_x` のランダム化）のため、**サンプル毎・エポック毎に
`export_root_margin`（ネットワーク共有）上のraw画像を都度読み直す**設計になっている
（`dataset-export-root-migration.md` 決定18で「`RawShiftImageFolder`/`process_image`自体は
無改修」として確定した既存設計）。color側は`process_annotated_images`で一度だけpool化・
ローカル保存（`training/4_dataset/`）した画像を読むため、この制約を受けない。

## 決定事項

1. **対象は monochro の raw-shift 読み込み経路のみ**。color側の学習ロジック・DataLoader構築は
   変更しない（`dataset-export-root-migration.md` の既存制約「マージン対応はmonochroのみ」を維持）。
2. **1回のパイプライン実行（1色番）の間だけ存在する、一時的なローカルキャッシュとする**。
   - 実行開始時（`train/monochro.py`のDataLoader構築部分、`RawShiftImageFolder`生成前）に、
     対象色番の`export_root_margin/{dataset_id_monochro_margin}/binary/{color}/`配下を
     ローカルの固定パス（`training/_cache/raw_shift_margin/`）へ一括コピーする。
   - `RawShiftImageFolder`の`raw_root`にはこのローカルキャッシュパスを渡す
     （ネットワークパスは直接渡さなくなる）。
   - パイプライン実行の冒頭でキャッシュ先を**必ず空にしてから**コピーする（前回・別色番の
     残留物を残さない。差分判定・世代管理は行わない）。
3. **キャッシュの生存期間は「今回の学習実行中のみ」**。実行完了時に明示的に削除するのではなく、
   **次回実行の冒頭でのクリア**に統一する（実行が異常終了した場合でも次回開始時に必ず
   クリーンな状態から始まるため、finally句等での後始终処理を追加する必要がない・実装が単純）。
4. **整合性検証は行わない**。実行ごとに全量を作り直すため、「ネットワーク側が更新されたのに
   キャッシュが古い」という不整合は構造的に発生しない（差分同期・manifest比較などは不要）。
5. **ディスク使用量**: 色番あたり実測 数GB〜10GB程度（例: 030の良品4064枚×平均2.4MB≈9.8GB）。
   同時に存在するキャッシュは常に1色番分のみ（`common.parallel_train`は monochro/color の
   GPU並列のみで、**再学習ジョブ自体の同時実行は1本**・FIFO、`tech.md`記載）。
   実測: D:ドライブ空き65GB（2026-08-20時点）に対し十分な余裕。
6. **既存の`use_raw_shift_dataset`config-gateは維持**。無効時（`false`）はこのキャッシュ処理自体を
   スキップする（従来のマージンなし学習パスに影響しない）。

## 検討した代替案

1. **差分同期（manifest比較・`_copy_if_new`方式）**: 既存コードの`_copy_if_new`パターンに
   倣う案。不採用理由: 再学習ジョブは同時1本・色番毎に他色番のキャッシュを保持する必要がなく、
   差分判定のための状態管理（manifestファイル・mtime比較）を追加する複雑さに対し、
   「毎回作り直す」の単純さで得られる正しさ（不整合が構造的に起きない）のほうが本用途に見合う。
2. **全色番を永続的にローカルキャッシュ**: 検討したが、35色番規模×色番あたり数GB〜10GBで
   ディスク容量（空き65GB）を明確に超えるため不採用（実測により確定）。
3. **1_download/2_staging構造の復活**（`dataset-export-root-migration.md`で既に却下済みの案）:
   本ADRの対象は`RawShiftImageFolder`が直接読むraw画像のみであり、`dataset/manager.py`が
   処理する`pool`/`dataset`構造とは別経路。同ADRの却下理由（「中間ファイルコピーの手間を省く」）
   は pool 化フロー自体の話であり、本件（学習ループ内の繰返し読み込み削減）には適用されない
   ため、却下の再評価ではなく対象が異なると判断した。
4. **ネットワーク帯域自体の増強（インフラ側対応）**: リポジトリ外の変更であり本ADRのスコープ外。
   将来的な選択肢として残すが、今回は対象としない。

## 制約 / 非目標

- **非目標**: 損失関数・モデル構造・学習ループ本体・`crop_offset_x`によるシフトaugmentationの
  意味そのものの変更。変更は読み込み元パスの切替のみ。
- **非目標**: color側の学習ロジック・DataLoader構築（変更しない）。
- **非目標**: キャッシュの世代管理・LRU・複数色番の同時キャッシュ（同時実行が1本のため不要）。
- **制約**: `training/_cache/`はリポジトリに含めない（`.gitignore`対象・実行時生成物）。

## 検証基準（ゲート）

- 単体テスト: キャッシュ生成関数が対象色番のカテゴリ配下の全画像をコピーすること、
  実行前に既存キャッシュ内容をクリアすること（前回色番の残留がないこと）を確認するテストがgreen。
- 統合確認: 912の学習実行で、`RawShiftImageFolder`が実際にローカルキャッシュパスを読んでいること
  （ログ・パス確認）、及び学習ループのit/sが030・579実測（1.64 it/s付近）より明確に改善していること。
- ロールバック確認: `use_raw_shift_dataset=false`時にキャッシュ処理がスキップされ、
  従来のマージンなし学習パスが従来通り動作すること（既存回帰テストで確認）。

## 見直し条件

- 将来、再学習ジョブの同時実行数が1本から増える設計変更があった場合、本ADRの前提
  （同時に存在するキャッシュは1色番分のみ）が崩れるため、再評価が必要。
- ディスク空き容量が本キャッシュ運用を圧迫する規模まで減少した場合、キャッシュ先ボリュームの
  見直しが必要。

## 変更履歴
