# 検査AIモデルのドメインシフト診断（虚報・見逃し原因分析）

## 概要

外観検査AI（EfficientAD系 teacher-student異常検知）は、学習データが持つ特定の輝度・シャープネス・質感の分布にキャリブレーションされている。撮像環境（照明・ピント・カメラ位置・号機）が学習後に変化すると、正常品が虚報になったり、逆に欠陥を見逃す。**「学習データの分布から外れた」ことが異常スコアの本質**であり、ボケていても鮮明すぎても同様に異常側へ振れる（[567番の実例](../../../.kiro/specs/retraining/st-augmentation-sharpness-robustness.md)：ピントを両方向にずらすとどちらもNG率が悪化した）。

本skillは、原因を「物理的な撮像環境ドリフト」と「ソフトウェア側の不整合（閾値取り違え・正規化方式）」に切り分け、対処方針（現場調整 → 再学習 → augmentationは保険）を判断する手順を提供する。

## 診断フロー

```
1. 分布比較（統計）      … 輝度(mean/p1/p99)・シャープネス(Laplacian分散)を学習データ vs 実機画像で比較
2. 実測で裏付け          … 実際にONNX推論に通し、スコア・NG率で確認（統計的近さ≠実スコアの近さ）
3. 視覚確認              … 画像を並べて目で見る（ボケ/ノイズ/白飛び。外れ値は撮像失敗の可能性を先に疑う）
4. 原因の切り分け        … 物理的ドリフト か ソフトウェア側の不整合(閾値取り違え・正規化方式) か
5. 対処方針の判断        … 下記の判断ツリー
6. 感度ゲートの固定      … 虚報対策の評価前に「見逃しが増えていないか」の合格基準を先に決める
7. 恒久対策              … 保守後ヘルスチェック・号機別閾値較正の運用化
```

## Step 1-2: 統計比較と実測（最重要な落とし穴）

輝度・シャープネスの分布比較（mean/p1/p99、Laplacian分散）は入口として有効だが、**「統計的に近い」ことと「実際のスコアが低い」ことは一致しない**。567番の実例では、輝度統計が最も学習データに近かった照度470が、実際のNG率では100%（照度460は72.7%）という逆転が起きた。個々の画像の偶然のばらつきの影響が統計指標には現れないため。

→ **判断の根拠は必ず「実際にONNXモデルへ通したスコア・NG率」を主、統計的な近さは補助情報として使う。**

## Step 3: 視覚確認で外れ値を先に除外する

異常に高いスコアの画像が混ざっていたら、まず「ドメインシフトの一部」と決めつけず、**撮像自体の失敗**（白飛び・露光過多・フラッシュ不具合など）を目視で疑う。567番の実例では、ある設定の最大スコアが他の10倍近い値になっていたが、実体は白飛びした失敗画像1枚で、除外すると評価が大きく改善した。

## Step 4: 原因の切り分け

| 原因カテゴリ | 確認方法 | 典型例 |
|---|---|---|
| 物理的ドリフト | 輝度・シャープネスの分布差、現場の保守履歴（照明交換・清掃・再取付） | 照明交換でカメラ位置がわずかにズレ、輝度・シャープネス両方が同時にズレた |
| ソフトウェア側の不整合 | 実機側の推論コード（閾値フィールドの取り違え、`score_type`の解釈）、`model.py`の正規化方式が学習・推論で一致しているか | 閾値メタデータを無視して固定しきい値と比較している 等 |

両方あり得るので、**片方を確認して満足せず両方チェックする**。

## Step 5: 対処方針の判断ツリー

```
物理的な原因(照明再取付・清掃・レンズ調整)を特定できるか？
├─ Yes → まず現場調整（照度→ピントの順に1変数ずつ切り分けて撮り直す）
│         各調整後に少数枚(5〜10枚)を実測スコアで確認しながら収束させる
│         目標域に届く・再現できる → 解決。ここで終了
│         再現性がない/届かない → 下へ
└─ No / 現場調整で不十分
          → 「今の実際の環境」を新標準として、そのデータで再学習（主対策）
             augmentation強化は「将来の小さなドリフトへの保険」であり、
             今回級の大きな分布ズレを埋める道具ではない（位置づけを混同しない）
```

**現場調整を優先する理由**: ソフトウェア側で吸収しようとする前に、まず物理的な原因（今回だけ起きた既知の変化）に対処する方が確実で安価。augmentationでの吸収は「保険」の位置づけであり、再学習に代わる主対策にはならない。

## Step 6: 感度ゲート — 虚報対策より先に固定する

augmentation強化や閾値の緩和は、虚報(FP)を下げると同時に**欠陥への感度(見逃し, FN)を犠牲にするリスク**がある。虚報の改善だけを見て採否を決めると、実際には検知率が大きく落ちたモデルを採用してしまう。

- **感度ゲートを先に決めてから**虚報側の実験を評価する（例: 既知の欠陥サンプルの検知率100%を必須条件にする）
- **brightness系のaugmentationは特に危険**。局所的な輝度変化は欠陥（黒点・薄い汚れ）そのものの見え方と同種のため、輝度方向の許容を広げることは「欠陥をノイズとして無視するよう教える」ことに等しい。虚報が最良でも感度が壊れているケースが実際に起きた（虚報1.7%だが欠陥の6割を見逃した実例）
- 逆に、**シャープネス方向のaugmentation（sharpen）は欠陥信号と直交する傾向があり、虚報と感度が同時に改善するケースがある**。同じ「augmentation」でも軸によって安全性が異なることを踏まえて優先順位をつける

### 感度検証で陥りやすい罠

| 罠 | 実際に起きたこと | 対策 |
|---|---|---|
| n小サンプルでの判断 | 欠陥サンプルがn=1しかない状況で、構成間のスコアの僅差を判断材料に使い、後で「aug強度と単調な関係がない」ことが判明して自己修正した | n=1〜数枚のスコアは「大きく外れた構成の棄却」の補助証拠にしかならない。合格圏内の構成の優劣判定には使わない |
| cross-color評価 | 色番Aのモデルで色番Bの欠陥を採点すると検知率100%だったが、色番B自身のモデルで採点すると60%だった（閾値が各色番の良品分布で較正されるため、他色番の画像は一律高スコアになりOOD扱いされる） | 感度評価は**当該色番自身のモデル**で行う |
| 短縮学習での優劣判定 | スクリーニング用の短縮学習では「強くするほど良い」と単調に見えたが、フル長で学習すると順位が逆転した | 短縮学習は「効くか効かないかのスクリーニング」にのみ使い、**構成間の優劣判定は必ずフル長で行う** |
| 複数変更の同時投入 | 2つの改善策(強sharpen + blur)を同時に入れると、それぞれ単独より劣化した（負の相互作用） | 1パラメータずつ切り分けて検証する。「両方の勝ち筋を足す」は機能しないことがある |

## Step 7: 恒久対策（再発防止）

- **撮像系ヘルスチェックの標準化**: モデルと一緒に学習ドメインの基準統計（輝度mean/p1/p99・シャープネス・良品スコア分布）を保存し、照明交換・清掃・レンズ調整などの保守後に、良品数枚をスコアリングして基準統計と照合してから生産再開する運用にする
- **号機別の閾値較正**: モデル（重み）は共通のまま、設置時・保守後にその号機の良品N枚をスコアリングして閾値だけを較正する。augmentationで良品分布を広く鈍く学習させるより、感度を犠牲にしない

## このプロジェクトでの制約（要確認）

- augmentationパラメータの調整（`training/conf/config.yaml`の値変更）は既存の範囲内で自律できるが、**augmentationの新規実装（例: ST側へのsharpen/blur追加）はCLAUDE.mdの学習ロジック変更制限に触れるため、進める前に承認とADR記録が必要**（`.kiro/specs/retraining/`配下）。詳細は `CLAUDE.md` の「やってはいけないこと」節を参照
- 再学習・現場調整の実験は3.5時間前後かかるため、複数構成を試す場合は事前に判断ルール（有意性のしきい値・停止条件・感度ゲート）を固定してから自律実行する方が場当たり的な反復を防げる

## Quick Reference: 実測に使う指標

| 指標 | 計算方法 | 見るもの |
|---|---|---|
| 輝度 | `mean` / `p1`（暗部） / `p99`（明部） | 学習データとの重なりの有無。重なりがなければ明確なドメインシフト |
| シャープネス | Laplacian分散（`cv2.Laplacian(img, cv2.CV_64F).var()`） | 値が低い=ボケ、高い=鮮明すぎorノイズ増。学習データの範囲との差 |
| 実スコア | 学習済みONNXモデルへ通した異常スコア（`para.json`の閾値と比較） | 統計指標より優先する最終判断材料 |

実測コードの最小例は `references/measurement-snippet.md` を参照。
